- `legere_api36`: pre-existing phone AVD (pixel_6), not used yet.
- KVM works. **The emulator is fragile in this environment**: with `-gpu swiftshader_indirect -no-window` it segfaulted (exit 139). With `-gpu host`, launched fully detached (`setsid nohup … &`), it booted. The first boot reported adb `unauthorized` until the AVD was started with `-wipe-data`. ## PDF and database results (`mapreduce.pdf`, 13 pages, RC4 owner-password only)

| Metric | Linux (debug) | Android emulator (debug, x86_64) |
|---|---|---|
| Open | 82 ms | 129 ms |
| Password prompts | **0** | **0** |
| Pages / size | 13 / 612x792 pt | same |
| Render page 1 at 1x (612x792) | 14 ms | 32 ms |
| Render page 1 at 3x (1836x2376) | 18 ms | 47 ms |
| 512x512 tile from the 3x page | 3 ms | 7 ms |
| Raw text + char rects (page 1) | 22 ms, 4,124 chars / 4,124 rects | 42 ms, same counts |
| Structured text, reading order (page 2) | 53 ms, 1,332 fragments | 89 ms, same |
| Drift insert + select + `sqlite_version()` | 1 row, SQLite 3.53.4 | same |

(The first Linux run measured faster, 41 ms open / 8 ms render, so these numbers vary by a factor of about 2 between runs. Treat them as order of magnitude, not benchmarks. Debug builds, emulator on software-ish virtualization.)

Findings:
- **Encrypted-but-openable PDFs open silently.** The fixture is flagged RC4-encrypted with an empty user password; `PdfDocument.openFile` with a password provider opened it with zero prompts on both platforms. The importer should still pass a provider so a real user password triggers a prompt.
- **Tiled rendering is viable.** A 512x512 tile at 3x takes 3 to 7 ms, which is well inside a frame at 60 Hz and workable at 120 Hz with a small prefetch ring.
- **Character rects come free**: one rect per character, so word-snapped highlighting needs no extra extraction. Rects are in **PDF space (origin bottom-left, `top > bottom`)**, so the page-space conversion in SPEC §4.2 (origin top-left) must flip y. Noted for M3.
- **Reading order is better than feared.** `loadStructuredText()` returned page 2's two-column body as left column top-to-bottom, then right column (92 line starts, identical on both platforms). Fragments are word-level and whitespace-level (1,332 on one page), so the text index is large: store it compactly. This lowers SPEC §19 risk 3 for this paper; it is one paper, so the risk stays open for other layouts.
- API correction: `PdfPage.loadText()` returns `PdfPageRawText` (text + char rects only). Fragments and reading order come from `loadStructuredText()`.

## Pointer probe: Wacom on Linux and Tab S9 / S Pen (done)

`lib/spikes/pointer_probe.dart` logs every raw pointer field to JSONL, tagged by phase. Wacom tablet, session: Wayland (KDE Plasma, Fedora 44). Tab S9 (SM-X710, Android 16, 1600x2560) with S Pen, debug build over adb.

Logs (local only): the S9 log is `probe_android_1792415281517.jsonl`, 10,485 lines (9,829 stylus and 648 touch events); `~/Documents/probe_linux_1792414796248.jsonl` (Wayland, 5,160 stylus events) and `~/Documents/probe_linux_1792414977311.jsonl` (`GDK_BACKEND=x11`, 3,914 events). Both are local, not committed.

| Check | Wacom, Wayland (GTK tablet input) | Wacom, `GDK_BACKEND=x11` (XWayland) | Tab S9 + S Pen |
|---|---|---|---|
| Pointer kind | **`stylus`** on every pen event | **`mouse`** for everything | **`stylus`** (pen), `touch` (finger); no mouse |
| Pressure | **0.00 to 0.98**, hundreds of distinct values per stroke; light about 0.33, hard about 0.91 | **fixed 1.0** (min = max = 1.0) | **0.00 to 1.00 range reported; real strokes reached 0.09 (light) to 0.61 (hard)**, 280 to 1,140 distinct values per stroke. Needs a pressure curve (S Pen rarely reports near 1.0) |
| Event rate during a stroke | **125 Hz** (8 ms steps) | not measured | **about 500 Hz** (2 ms steps), about 4 samples per frame at 120 Hz; touch 125 Hz |
| Hover events | yes (`kind: stylus`), but `distance` is always 0 | plain mouse hover | **yes, with `distance`** 0 to about 104 (raw units; `distanceMax` is reported as 0, so it cannot be normalised from the event) |
| Tilt / orientation | always 0 | always 0 | **yes**: tilt 0.07 to 0.58 rad, orientation varies |
| Tip contact `buttons` | 1 | 1 | 1 |
| Barrel button 1 | `buttons` 4 (5 with tip down) | not distinguishable | **`buttons` 2** (no tip bit while the button is held: 2, not 3) |
| Barrel button 2 | `buttons` 2 (3 with tip down) | not distinguishable | none (S Pen has one button) |
| Barrel button while only hovering | **not reported** (hover events always `buttons: 0`) | n/a | **reported**: hover events carried `buttons: 2` while the button was held (27 of 28) |
| Eraser end (`invertedStylus`) | **no events observed**; the `eraser-end` phase has no data, so it was not exercised or not reported | none | none (S Pen has no eraser end) |
| Palm / touch rejection | n/a (pen tablet has no touch) | n/a | **zero touch events** while the pen hovered and wrote with the palm resting, so Samsung's OS-level rejection handled it completely |

Findings:
- **Pressure ink works on Linux under a native Wayland session** and not under X11/XWayland. The app must run as a Wayland client (the Flutter default on this system, unless `GDK_BACKEND=x11` is forced).
- Under X11 the pen is a plain mouse: no pressure, no stylus kind, no button distinction. That is SPEC §2 outcome (b) and is what the app falls back to.
- A barrel button is only visible once the tip is down. It cannot be used as a hover-time modifier. The planned "barrel button = temporary erase" (SPEC §7.2) still works because it is read during contact. Mapping to implement: `buttons & 4` is barrel button 1, `buttons & 2` is barrel button 2 (these are Flutter's `kSecondaryStylusButton` and `kPrimaryStylusButton`; confirm names at M4). Make the mapping a setting, since pens differ.
- 125 Hz means a stroke gets a point every 8 ms. That is a good input rate for ink on a 60 Hz or 120 Hz display; prediction (SPEC §5.5) is still useful for the last frame.
- No hover distance and no tilt: "pen near" previews can show position only, and shading by tilt is out.
- Eraser end is **unconfirmed**. Treat the eraser as a toolbar tool and a keyboard shortcut on Linux; honour `invertedStylus` if it ever arrives.

S Pen findings (Tab S9):
- **Pressure, tilt, hover distance, and the side button all work**, at about 500 Hz. This is the richest input of the two devices. Ink should use pressure with a configurable curve (soft default) because normal writing peaks around 0.1 to 0.6, not 1.0.
- **The side button is visible during hover** on the S Pen (`buttons: 2`), unlike the Wacom on Linux (button only seen during contact). Button bits are device-specific: Wacom button 1 is `4` and button 2 is `2`; S Pen button 1 is `2`. The app must not hard-code one mapping; add a "learn my pen button" step in settings that records which bit changes when the user presses the button.
- **Palm rejection**: with a resting palm, **no touch pointers reached Flutter at all**. The OS rejects the palm, so the app-level lockout in SPEC §7.3 (items 2 to 4) is a safety net, not the primary mechanism. Keep it small and testable; do not tune it blind.
- **500 Hz means batching**: several samples arrive per frame. The ink pipeline must consume every sample (SPEC §5.5 already says to) and not draw one point per frame.
- **Touch input** reports constant pressure 1.0 and a contact radius of about 1 to 8 (`radiusMajor`), enough for the large-contact filter if it is ever needed.
- The probe's finger-draws-lines behaviour in the `finger-pan` and `two-finger-pinch` phases was expected: the probe has no gesture logic and draws every pointer. The real app routes touch to pan and pinch (SPEC §7.2).

**Linux pressure-ink go/no-go: GO on Wayland** (pressure, 125 Hz, stylus kind, two barrel buttons). The X11 fallback is constant-width ink. Eraser end stays an open item until re-tested.

## Decisions made in M0

- Linux pressure ink: GO on Wayland; constant-width fallback on X11.
- Android S Pen: full pressure, tilt, hover distance, and button; palm rejection handled by the OS. Pen button bit mapping must be configurable.
- minSdk 24, targetSdk 36. App id fixed. `sqlite3_flutter_libs` dropped. Reading order from `loadStructuredText()`.
- Spike code stays in `lib/spikes/` until M1, then is deleted.

## How to run the spikes

```
# PDF + Drift (Linux): build then run the binary directly; report goes to OUT
flutter build linux --debug -t lib/spikes/pdf_spike.dart \
  --dart-define=PDF=$PWD/test/fixtures/mapreduce/mapreduce.pdf --dart-define=OUT=/tmp/report.json
build/linux/x64/debug/bundle/aether

# PDF + Drift (Android emulator)
flutter build apk --debug --target-platform android-x64 -t lib/spikes/pdf_spike.dart \
  --dart-define=PDF=/data/local/tmp/mapreduce.pdf --dart-define=OUT=/sdcard/Download/aether_report.json
adb push test/fixtures/mapreduce/mapreduce.pdf /data/local/tmp/ && adb install -r build/app/outputs/flutter-apk/app-debug.apk

# Pointer probe on Linux (Wayland, then X11); the probe fixed a log-flush bug found during the X11 run
flutter build linux --debug -t lib/spikes/pointer_probe.dart
build/linux/x64/debug/bundle/aether                      # log: ~/Documents/probe_linux_<ts>.jsonl
GDK_BACKEND=x11 build/linux/x64/debug/bundle/aether

# Pointer probe on the Tab S9 (arm64)
flutter build apk --debug --target-platform android-arm64 -t lib/spikes/pointer_probe.dart
adb install -r build/app/outputs/flutter-apk/app-debug.apk
adb pull /sdcard/Android/data/com.ritvijsrivastava.aether/files/   # the probe_*.jsonl
```
